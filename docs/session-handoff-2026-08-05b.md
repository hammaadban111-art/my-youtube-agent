## What this project is

A fully unattended faceless-YouTube-Shorts channel. Free tier everywhere.
GitHub Actions runs it; nothing runs on a laptop.

- **Niche:** unsolved mysteries and bizarre history.
- **`daily.yml`** — 4x/day (01:07, 06:07, 11:07, 16:07 UTC). Writes a script
  with Gemini → fact-checks it against Wikipedia → edge-tts narration →
  Pexels B-roll → moviepy assembly → YouTube upload → records → dashboard.
- **`followup.yml`** — every 3h. Measures views/likes/comments/retention for
  every tracked video until it turns 30 days old, then freezes it forever.
- **`niche_scan.yml`** — weekly niche benchmark scan.
- **`tests.yml`** — pytest on every push. Deliberately NOT an upload gate.
- **`reupload.yml`** — new, manual only. See item 3 below.
- **Dashboard** — generated by `agent/dashboard.py`, published by
  `scripts/publish_dashboard.sh` to a **separate public repo** over an SSH
  deploy key. This repo stays private. The dashboard has no credentials.

## What shipped this session

### 1. Uploads are on the quota ledger (they never were)

`videos.insert` costs **1,600 units** of a 10,000/day cap — 16% for one
upload — and `record_units()` was only ever called from `dashboard.py` and
`followup.py`. Every upload this channel has ever made was invisible to the
ledger. `videos.delete` costs 50 and was likewise untracked.

- `quota.record_upload(video_id)` books it, **keyed by video id**, so the
  three callers that now book it (the upload path, the re-upload path, the
  reconciliation sweep) can never double-count.
- `quota.reconcile_uploads(records)` books any of today's uploads the ledger
  missed. Called from `dashboard.build_data()`, which both workflows run, so
  the ledger self-heals within one follow-up cycle.
- Two thresholds, deliberately different:
  - `fits_in_cap(units)` — hard 10,000 cap. Gates the **scheduled** upload.
    Refusing that at 70% would halt the channel over a comfort line.
  - `has_headroom_for(units)` — the existing 70% reserve. Gates
    **discretionary** spend: 30-day final refreshes and re-uploads.
- `main.py` now refuses before rendering rather than after.

**Verified on the real ledger:** 179 → 1,779 units. It booked `5zSVFkP4WVM`
(01:56 PT today) and correctly did **not** book `7-F4mLwE1mI`, which was
21:26 PT **yesterday** despite sharing a UTC date. The ledger resets on
Google's own midnight-Pacific boundary; any sweep that filters on UTC date is
wrong by up to 8 hours.

### 2. B2 duplicate-topic detection — built, and held to 2026-08-07

Group B lands one change at a time, ≥48h apart. B1 (tags) landed 2026-08-05,
so B2 activates 2026-08-07. It is **built and merged but gated**, not waiting
to be written.

- `history.append_entry(title, topic_subject)` records the subject from now
  on. Recording is not a change YouTube sees, so it starts immediately — the
  data has to exist before detection switches on.
- `history.load_recent_subjects()` / `normalize_subject()` /
  `is_duplicate_subject()`. Lookback widened 30 → 60.
- Normalization drops a trailing Wikipedia disambiguator, punctuation,
  apostrophes and generic descriptor words (case, mystery, incident,
  disaster…). Three match rules: identical normalized form, same significant
  words in any order, or a strict subset sharing ≥2 words.
- `script_writer` lists the subjects in the prompt AND rejects a duplicate
  script, re-asking with the repeat named.
- `DUPLICATE_BLOCK_AFTER` (env / repo Variable, default `2026-08-07`) gates
  the prompt block, the widened lookback and the rejection together.

**Backfilled 29 subjects** into `history/topics.json` from the existing
records, then replayed detection over the real 32-entry history: **2 repeats
flagged, 0 false positives across 29 subjects.**

- `Tamam Shud case` — `qnAWjYhNlck` (2026-07-30T14:09Z) and `2NiZ95wtNX0`
  (17:47Z). The known pair.
- **`Devil's Kettle` — published TWICE and never noticed**: `p2N0xOZxIUA`
  (2026-08-01, 842 views) and `efMGQGVzh8Y` (2026-08-04, 929 views), under
  near-identical titles. Three days apart, comfortably inside the old
  30-entry window — so the prompt-side avoid list **had** the information and
  the model ignored it anyway. That is the argument for hard rejection over
  prompt steering, and it is new evidence not in any earlier handoff.

**Design decision worth keeping:** when both generation attempts return a
duplicate, the run **publishes the repeat and records a degradation** rather
than raising. A duplicate costs 1,600 units and a repeat; a wrongly-blocked
run costs the slot and leaves nothing. Same reasoning `tests.yml` already
states for not being an upload gate.

**Trap found:** an unset GitHub repo Variable arrives as an **empty string**,
not as absent, so `os.getenv("X", default)` returns `""` and the default
never applies. That would have read as "no hold" and released B2 early by
omission. Uses `(os.getenv(...) or default)` now, with a test.

### 3. Replace button — delete + re-upload from a saved bundle

New: `scripts/reupload_video.py`, `.github/workflows/reupload.yml`, and a
confirmation dialog on each video row in the dashboard.

**Order of operations, and why:** the replacement is uploaded **first**, and
the old video is deleted only after that succeeds. The reverse order is one
failed render away from having deleted a video with nothing to put in its
place. Upload-then-delete's worst case is a duplicate you remove by hand.

Refusals, all before anything is rendered:
- no stored record for that id, or no bundle
- quota short — 1,650 units must leave the 70% reserve intact
- the token cannot delete (see the blocker below)
- the velocity guardrail is blocking (a replace is still an upload)

If the bundle carries `visual_queries_are_legacy_generic`, the queries are
regenerated first (`script_writer.regenerate_visual_queries`, one Gemini
call) instead of faithfully reproducing the generic footage the anchored-
visual fix removed. A normal replace makes **zero** Gemini calls.

The YouTube description was never persisted on any record, so a replace
writes one from the bundle's own text. Its hashtags matter beyond the
description — `build_tags()` reads them, so they carry the subject into the
new video's tags.

**The dashboard cannot delete anything itself, by design.** It is a static
page on a separate public repo with no credentials. The button opens a
confirmation dialog and then sends you to the workflow in this private repo,
where GitHub's own login is the real authorization. The workflow then makes
you retype the video id, and `dry_run` defaults to **true**.

### 4. The graph-update instruction

`~/.claude/CLAUDE.md` and `.agents/rules/graphify.md` now say: after any task
that **changed code** (source, behaviour, workflow/config, or docs about the
system), run `/graphify --update` automatically before ending the turn —
without being asked. Skip it on turns that changed nothing. Use the **skill**
form, not the bare `graphify update .` CLI: the CLI is AST-only and silently
leaves docs and semantic edges stale, which is exactly how the doc pass here
went stale for a whole phase.

## Traps a fresh session should know

- **Verify by running it, not by reading it.** This has now caught real bugs
  four separate times on this project: bad tags that passed unit tests, an
  artifact glob that would have stored ~40MB of junk per run, the
  empty-string env-var default above, and the missing delete scope. Green
  tests are not evidence.
- **`graphify-out/` is gitignored.** A fresh clone has no graph. Rebuild with
  a full `/graphify .` — the doc/semantic pass needs subagents (or a Gemini
  key, but **do not** use the repo's `GEMINI_API_KEY` for it: that 20/day
  free tier is the video pipeline's budget).
- **`graphify update` misreports freshness.** It can print "No code-graph
  topology changes detected" and leave the report stamped at an older commit
  while `graph.json` does hold the new nodes. Don't trust "Built from
  commit"; probe `graph.json`.
- **PLAN.md is never auto-updated.** Every changelog entry is hand-written.
  There are no hooks configured — the "automatic graphify update" rule is an
  instruction to the model, not harness automation.
- **The dashboard is two files.** `agent/dashboard.py` holds the page as a
  `PAGE` string; `public/index.html` is generated from it. Edit the Python,
  never the HTML.
- **`data.json` and `index.html` deploy independently.** A new page shipped
  before the next CI run must degrade gracefully against an older
  `data.json` — the replace button does (it renders nothing without the
  `quota` and `reuse` keys).
